# Аудит безопасности AnimeShadow

Дата: 2026-09-15
Проверено вручную: живые HTTP-запросы к API (`http://localhost:4000`), чтение кода (`apps/api`, `apps/web`, `packages/*`), проверка конфигурации (`.env`, `docker-compose.yml`, `deploy/Caddyfile`).
Формат: находка → как проверял → критичность → статус.

## 🔴 Критично

### 1. `JWT_SECRET` был установлен в placeholder-строку из документации
**Файл:** `.env`
**Было:** `JWT_SECRET=change-me-to-a-long-random-string-at-least-32-chars`

Эта строка — не случайный секрет, а буквальный текст подсказки из `.env` и `README`. Она удовлетворяет валидации `min(32)` в `apps/api/src/config/env.ts`, поэтому приложение стартовало без единой ошибки — но любой, кто знает этот (публично документированный) placeholder, может подписать JWT для **любого** `userId` и получить полный доступ к чужому аккаунту, включая `/api/me/profile`, `/api/admin/*` (если аккаунт админ) и т.д.

**Как проверял:** вручную подписал HS256-токен на этой строке (`sub` = чужой пользователь, `exp` в будущем) — API принял его как валидный до замены секрета, и `/api/auth/me` вернул чужие данные.

**Статус: ✅ ИСПРАВЛЕНО.** Сгенерировал новый случайный секрет (`crypto.randomBytes(48)`, 384 бита энтропии) и заменил в `.env`. Все ранее выданные токены (включая мои тестовые) теперь отклоняются (`401`). Сервер перезапущен с новым секретом, регистрация/логин работают.

**Что сделать дополнительно:** при деплое на прод (`deploy/`) убедитесь, что на сервере `.env` тоже содержит случайный секрет, а не тот же placeholder — он не подтягивается автоматически из репозитория.

## 🟠 Высокая критичность (не исправлено — только описано, по вашему решению)

### 2. Rate limiting обходится подделкой `X-Forwarded-For`
**Файл:** `apps/api/src/app.ts` (`trustProxy: true`) + `@fastify/rate-limit`

Fastify сконфигурирован с `trustProxy: true` без ограничения на конкретный доверенный прокси. `@fastify/rate-limit` ключует лимит по `request.ip`, который при `trustProxy: true` берётся из клиентского заголовка `X-Forwarded-For` — а его может прислать кто угодно.

**Как проверял:**
```
curl http://localhost:4000/api/genres                              → x-ratelimit-remaining: 405
# ... 400 запросов подряд ...
curl http://localhost:4000/api/genres                               → 200 (лимит НЕ исчерпан для реального IP? проверено отдельно)
curl -H "X-Forwarded-For: 198.51.100.42" http://localhost:4000/...  → x-ratelimit-remaining: 599 (свежая квота!)
```
После полного исчерпания лимита с реального IP один произвольный заголовок `X-Forwarded-For` тут же выдаёт полную новую квоту в 600 запросов/мин. Это полностью снимает защиту от брутфорса `/api/auth/login`, спама комментариев и т.д. — достаточно менять заголовок на каждый запрос (или использовать пул IP из заголовка).

**Рекомендация:**
- Если API стоит за Caddy (как в `deploy/Caddyfile`) — ограничить `trustProxy` конкретным IP/подсетью бэкенда (`trustProxy: ['127.0.0.1']` или IP самого Caddy), а не `true` (означает «доверяй любому X-Forwarded-For»).
- Добавить отдельный, более строгий rate limit конкретно на `/api/auth/login` и `/api/auth/register` (например, 5–10 попыток / 10 минут на IP+email), независимо от общего лимита — классическая защита от брутфорса паролей.
- Библиотека уже используется правильная (`@fastify/rate-limit`), проблема только в доверии к заголовку.

## 🟡 Средняя критичность

### 3. Content-Security-Policy нигде не выставлен
**Файлы:** `apps/api/src/app.ts` (`contentSecurityPolicy: false` — с комментарием «фронтенд сам поставит CSP»), `apps/web/index.html` (нет `<meta http-equiv="Content-Security-Policy">`), `deploy/Caddyfile` (нет `header` директивы).

Комментарий в коде обещает CSP на стороне фронтенда, но по факту его нет ни в `index.html`, ни в проде через Caddy. Само по себе это не уязвимость (React экранирует вывод, `dangerouslySetInnerHTML` в проекте не используется — проверено `grep`), но CSP — это защита второго эшелона на случай, если XSS всё же где-то возникнет (например, через будущую фичу или стороннюю библиотеку). Сейчас этого эшелона нет.

**Рекомендация:** добавить в `deploy/Caddyfile` блок `header` с базовым CSP (`default-src 'self'; img-src * data:; media-src *; frame-src https://kodikplayer.com https://*.libria.fun ...; script-src 'self' 'unsafe-inline'` — придётся разрешить домены Kodik/Alloha/AniLibria/шрифтов из-за iframe-плееров и Google Fonts), плюс `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` — сейчас статика отдаётся вообще без security-заголовков (они есть только у `/api/*` через `@fastify/helmet`).

### 4. `PRO_FOR_ALL=true` — временный флаг, легко забыть выключить
**Файл:** `.env` / `apps/api/src/config/env.ts`

Это осознанная временная настройка (открытое тестирование), но раз аудит — стоит явно напомнить: перед реальным запуском с платежами обязательно поставить `PRO_FOR_ALL=false`, иначе все пользователи бесплатно получают PRO.

### 5. Загрузка аватара не проверяет реальное содержимое файла
**Файл:** `apps/api/src/services/profile.service.ts` (`setAvatar`)

Проверяется только `data:image/(png|jpeg);base64,...` по regex и лимит 5 МБ — но не magic bytes самого файла. Можно прислать произвольные байты с правильным префиксом data-URL. Риск невысокий (Content-Type при отдаче жёстко выставляется сервером как `image/png`/`image/jpeg`, так что MIME-sniffing XSS не сработает), но лучше проверять реальный формат (например, через `sharp` — уже стандартная библиотека для Node, заодно можно и ресайзить/оптимизировать аватар на лету).

## 🟢 Мелкие замечания

- **`/api/auth/me` с намеренно битым JWT (`alg: none`, обрезанная подпись)** возвращает `400 Bad Request` в формате Fastify по умолчанию вместо единого формата ошибок приложения (`{"error":{"code":"UNAUTHORIZED",...}}`, как в остальных местах). Не уязвимость, но неконсистентно — `authenticate` в `plugins/auth.ts` этот путь не перехватывает, потому что ошибка возникает раньше, ещё при разборе токена библиотекой `@fastify/jwt`.
- **`TELEGRAM_BOT_TOKEN` лежит в открытом виде в `.env`.** Файл в `.gitignore` и никогда не коммitился (проверил `git log -- .env`, `git ls-files` — чисто), так что утечки через git нет. Просто напоминание: не коммитьте, ротируйте токен, если он когда-либо «утекал» в чат/скриншот/логи.
- **`POSTGRES_PASSWORD=animeshadow`** — тривиальный пароль, совпадает с логином. Некритично для локальной разработки (порт 5433 закрыт от внешнего мира), но не переиспользуйте этот `.env` как есть на проде.
- Во время нагрузочного теста rate-limit (полсотни параллельных запросов) dev-сервер API пару раз перезапускался сам — стоит присмотреться к устойчивости под всплеск конкуррентности (не критично для локальной разработки, но полезно перепроверить на проде под реальной нагрузкой).
- В `apps/web/src/components/anime/watch-section.tsx` три React-хука (`useState`/`useEffect`/`useRef`) вызываются технически после `if (!displaySource) return null` — ESLint (`react-hooks/rules-of-hooks`) ругается. На практике `displaySource` никогда не бывает `null` в этой точке (компонент рендерится только когда `data.sources.length > 0`), так что бага в рантайме нет, но лучше поднять `return null` после всех хуков, чтобы линтер не «молчал» о реальной проблеме, если условие когда-нибудь изменится. **Не мой код — уже было так до этой сессии.**

## ✅ Проверено — уязвимостей не найдено

Всё ниже — живые попытки эксплуатации, не просто чтение кода.

| Категория | Что пробовал | Результат |
|---|---|---|
| **SQL-инъекции** | `' OR '1'='1`, `UNION SELECT email,password_hash...`, `'; SELECT pg_sleep(5)--` в `/api/search?q=`, `/api/auth/login` | Везде Prisma параметризует запросы — payload'ы просто искались как обычный текст, задержек/ошибок/утечек нет |
| **JWT-подделка** | `alg: none`, обрезанная подпись, изменённый `sub` со старой подписью | Все отклонены `401` |
| **IDOR** | Второй пользователь редактирует/удаляет чужой комментарий по его id | `403 FORBIDDEN` |
| **Mass assignment** | `role`, `isAdmin`, `proSince` в теле `/auth/register` и `/me/profile` | Zod отбрасывает неизвестные поля — роль всегда `USER`, PRO не проставляется |
| **Privilege escalation → admin** | Обычный пользователь дёргает `/api/admin/overview`, `/api/admin/users` | `403 FORBIDDEN`; роль перепроверяется из БД на каждый запрос (`requireAdmin`), не доверяет claim в токене |
| **Path traversal** | `/uploads/avatars/..%2f..%2f..%2fetc%2fpasswd` и вариации | `422` — regex на имя файла + проверка `normalize().startsWith()` |
| **SSRF через image-proxy** | `/api/img?u=` с IP метадаты (`169.254.169.254`), доменами-подделками (`evilshikimori.io`, `shikimori.io.evil.com`), non-https, userinfo-трюком (`shikimori.io@169.254.169.254`) | Везде `400` — строгий allowlist по хосту + обязательный `https:` |
| **Prototype pollution** | `__proto__`/`constructor.prototype` в теле `/me/profile` | `400`, не проходит |
| **CORS** | Запрос с `Origin: https://evil-attacker.com` | Заголовок `Access-Control-Allow-Origin` не возвращается — источник не в allowlist |
| **Доступ к `.env`/исходникам через веб** | `/.env`, `/package.json`, `/uploads/../.env` | `404` — не раздаётся |
| **DoS большим телом** | POST 10 МБ на `/api/auth/login` | `413` — лимит тела запроса работает |
| **XSS в комментариях** | `<script>alert(1)</script>` в теле комментария | Хранится как текст; `dangerouslySetInnerHTML`/`innerHTML` нигде не используется во всём `apps/web` — React экранирует при рендере |
| **Брутфорс логина (сам механизм сравнения)** | Логин с несуществующим email | Сравнение через bcrypt с фиктивным хешем даже для несуществующего пользователя — нет тайминг-атаки на перечисление email |
| **Заголовки безопасности API** | `curl -D-` | `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `Referrer-Policy`, `X-DNS-Prefetch-Control` — все на месте (`@fastify/helmet`) |

## Итоговые рекомендации по библиотекам/коду

Текущий стек уже выбран разумно — ничего менять не нужно, только донастроить:

1. **`@fastify/rate-limit`** — уже используется правильно, но `trustProxy: true` в `app.ts` нужно сузить до реального доверенного прокси (см. находку №2). Плюс отдельный строгий лимит на `/api/auth/*`.
2. **`zod`** — используется образцово почти везде (валидация тела/квери на каждом роуте, `.strict()`-подобное поведение по умолчанию отсекает лишние поля). Менять не нужно.
3. **`bcryptjs`, cost=12** — адекватно для 2026 года, менять не нужно.
4. **`@fastify/helmet`** — для API настроен хорошо; для статики на Caddy — добавить аналогичные заголовки + CSP вручную (helmet туда не дотягивается).
5. Для проверки реального содержимого загружаемых аватаров — можно взять `sharp` (уже стандарт в экосистеме Node/Fastify), он заодно решит и ресайз/сжатие.

## Работа над плеером (отдельная задача, не аудит)

Параллельно с аудитом реализован кастомный скин управления для HLS-источника (AniLibria) в `apps/web/src/components/anime/watch-section.tsx`: play/pause, шкала перемотки с индикатором буфера, громкость, скорость воспроизведения, полноэкранный режим — полностью свои контролы вместо нативных браузерных, для случая когда у тайтла есть прямой HLS-поток (не iframe). Для источников Kodik/Alloha (iframe) свой UI технически невозможен — это ограничение сторонних встраиваемых плееров, а не то, что можно обойти кодом.

`pnpm typecheck` и `eslint` на изменённый файл — чисто (кроме 3 предсуществующих warning'ов про порядок хуков, см. выше, не связанных с этой правкой). Живую проверку в браузере headless-автоматизацией довести до конца не удалось (headless Chromium/Edge в этом окружении не всегда до конца декодирует видео, хотя сеть/CORS/монтирование DOM я подтвердил через логи) — рекомендую открыть `http://localhost:5173/anime/20507-noragami` в обычном браузере и проверить визуально самостоятельно.
