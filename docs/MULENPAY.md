# Mulen Pay: включение оплаты

Интеграция выключена по умолчанию. Boosty продолжает работать. Настоящие платежи в ходе разработки не создавались.

## Что необходимо от магазина

В серверном `.env` задайте `MULENPAY_API_KEY`, `MULENPAY_SECRET_KEY`, положительный `MULENPAY_SHOP_ID` и `MULENPAY_PRICES_RUB` — JSON со строковыми суммами в рублях по существующим срокам `1`, `3`, `12`. Пока рублёвые цены не утверждены, оставьте `{}`. Долларовые цены PRO в проекте не меняются и автоматически не конвертируются.

Перед приёмом реальной оплаты заполните реквизиты оператора на странице `/legal`, проверьте согласованные с магазином параметры чека: в реализации сейчас `vat_code: 0`, `payment_subject: 4`, `payment_mode: 4`. Они должны соответствовать вашему договору с провайдером. Ключи нельзя помещать в переменные `VITE_*`.

После настройки проведите тест в кабинете провайдера. Только затем включайте `MULENPAY_ENABLED=true`. Миграция `20261017090000_support_payments` добавляет отдельную таблицу счетов.

## Подтверждение платежа

- Создание: `POST /api/payments`, авторизованный пользователь, явное согласие с актуальной редакцией документов, срок, UUID запроса и показанная пользователю сумма. Сумма пересчитывается на сервере; изменение цены требует обновить страницу.
- Возврат на `/support?payment=<UUID>` только открывает проверку. Сам переход не выдаёт PRO.
- Callback магазина: `POST https://animeshadow.online/api/payments/mulenpay/callback`, JSON с числовым `id` платежа. Остальные поля callback не считаются доказательством оплаты.
- Сервер самостоятельно запрашивает `GET https://mulenpay.ru/api/v2/payments/{id}` с секретным API-ключом. Сверяет ID, UUID, сумму и валюту. Только статус `3` даёт PRO. Статусы холда не дают доступ.
- Блокировки строк счёта и пользователя защищают от повторных и одновременных callback. Существующий остаток PRO и пробный период сохраняются; оплаченный срок добавляется один раз. Бессрочный PRO остаётся бессрочным.
- Проверка статуса пользователем ограничена владельцем счёта. Callback ограничен частотой запросов. Неизвестный ID не вызывает запрос к провайдеру.
- Повтор запроса с тем же UUID возвращает уже созданный ожидающий счёт. При неоднозначном тайм-ауте создания состояние остаётся `creating`: повторное списание автоматически не инициируется, счёт следует сверить в кабинете магазина.

## Документация и ограничение проверки

Использованы официальные [создание платежа](https://docs.mulenpay.com/pays/pays_create.html), [параметры и подпись](https://docs.mulenpay.com/pays/pays_request.html), [проверка статуса](https://docs.mulenpay.com/pays/pays_getdata.html).

Есть расхождение официальных материалов: текущая документация описывает SHA-1 от `currency + amount + shopId + secret`, а старый Node SDK в официальном репозитории добавляет перед секретом `uuid`. Реализация следует текущей документации. До включения реальных платежей необходимо подтвердить вариант подписи в кабинете/поддержке своего магазина тестовым платежом. Ответ API не имитируется, внешняя успешная транзакция пока не подтверждена.

Автоматические возвраты не создаются; обработка возврата оплаченного срока требует согласовать правила с магазином и условиями сервиса.
